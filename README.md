# CNI Embedded Systems Firewall Injection

A low-level security auditing and network isolation toolkit designed for Container Network Interfaces (CNI) on embedded and Linux systems. This project enables stealthy, runtime injection of custom `nftables` firewall rules directly into kernel subsystems by intercepting and manipulating application system calls via `ptrace`.

---

## Project Overview & Architecture

Container Network Interfaces (CNI) configure virtual network links (`veth` pairs) and bridge environments for containers. However, enforcing granular security policies across ephemeral container environments often requires deep kernel intervention.

This project bypasses standard user-space netlink utilities (`nft`) by attaching directly to container or management processes via process tracing (`ptrace`), dynamically rewriting socket communication buffers to inject raw binary Netlink firewall rules directly into the Netfilter subsystem.

---

## How We Listen to & Interact with CNI

1. **Interface Tracking:** Monitors virtual ethernet devices (`veth`) and bridge structures established by CNI plugins on the host or container network namespace.
2. **Chain Hooking:** Integrates with pre-existing kernel Netfilter chains generated by CNI firewall plugins (such as `CNI-FORWARD`, `CNI-ISOLATION-STAGE-1`, and `CNI-ISOLATION-STAGE-2`).
3. **Packet Traversal Inspection:** Evaluates packet counters and ingress/egress bindings to ensure rules intercept traffic according to the container's defined policies.

---

## Relation to PCIe & Hardware Interfaces

While software firewall injection executes within the kernel's network stack and CPU registers, it ties directly into hardware data paths:

* **PCIe NIC Association:** Firewall rules can be scoped to match traffic originating from physical or virtual network interface cards (such as SR-IOV Virtual Functions or PCIe-attached Ethernet controllers like `enp3s0`).
* **Meta-Expression Filtering:** The Netlink payload uses `nftables` meta expressions (`NFT_META_IIFNAME`) to enforce hardware-bound network boundaries as packets transition from PCIe DMA buffers into the kernel networking stack.

## How the Firewall Injection Works

The injection engine utilizes a multi-stage `ptrace` mechanism to force a target process into executing a Netlink message submission on its behalf:

### 1. Finding Writable Memory Slack (`find_writable_slack`)

* The tracer scans `/proc/[pid]/maps` to locate suitable writable memory regions (`r-w`) within the target process.
* It calculates an optimal high-address slack space to safely store the raw binary Netlink packet payload without corrupting application heap or stack data.

### 2. Remote Payload Staging (`remote_write`)

* Using `ptrace(PTRACE_POKEDATA)`, the injector writes the raw binary Netlink rule structure directly into the target process's address space.

### 3. Syscall Interception & Argument Swapping (`nf_inject_on_send_entry`)

* The injector intercepts the target process when it enters a `sendto` or `sendmsg` system call on a target Netlink socket file descriptor (`fd`).
* It captures original CPU register states (`PTRACE_GETREGS`) and swaps the buffer pointer (`rsi`) and length (`rdx`) to point directly to the hidden Netlink payload in the process's memory slack.

### 4. Re-issuance & State Restoration (`nf_inject_on_send_exit`)

* Once the kernel processes the hijacked `sendto` call—submitting the rogue firewall rule to the Netfilter subsystem—the exit hook intercepts execution.
* It restores original register states and rewinds the instruction pointer (`rip -= 2`) so the target application continues running transparently without crashing or realizing its socket was hijacked.

### 5. Binary Netlink Construction (`nf_build_rule`)

* Constructs raw Netlink messages (`nlmsghdr`, `nfgenmsg`, and nested `nlattr` attributes) targeting the `nftables` subsystem (`NFNL_SUBSYS_NFTABLES`).
* Serializes table names, chain names, PCIe interface metadata matchers, and immediate drop verdicts (`-1` / `NF_DROP`) into a compliant binary stream.
